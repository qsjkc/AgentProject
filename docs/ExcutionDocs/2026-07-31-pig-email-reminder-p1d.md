# 小猪邮件提醒双通道 P1-D 执行记录

## 1. 阶段结论

P1-D 选择“桌面通知 + 后端邮件”双通道，补齐桌面应用关闭时一次性提醒无法交付的问题。邮件是可靠性补充，不替代小猪在桌面上的动作、气泡、系统通知和待处理闭环。

当前代码已经完成，遵照本轮要求未启动应用、后端服务或安装包，也未执行测试、构建、数据库迁移和 SMTP 实发。因此本记录只代表静态实现完成，不代表运行验收通过。

## 2. 产品规则

- 新建提醒默认开启邮件，发送到当前登录账号的已注册邮箱。
- 创建成功文案明确说明到点会发送邮件。
- 邮件发送状态与桌面 `triggered_at` 完全解耦。
- 邮件发送成功不会阻止桌面端随后播放动作、显示气泡和系统通知。
- 用户完成或取消尚未发送的提醒后，邮件投递立即停止。
- 修改提醒时间会重新武装邮件；已发送提醒不会因无关字段修改而重复发送。
- 可以通过 API 为单条提醒关闭邮件，关闭后仍保留桌面提醒。
- 邮件正文只包含账号名、提醒标题和计划时间，不包含原始对话文本。
- 邮件使用动物身份文案；小猪主题为“小猪提醒你”。

## 3. 投递状态

提醒新增以下邮件字段：

- `email_enabled`：单条提醒是否启用邮件。
- `email_status`：`pending`、`sending`、`retrying`、`sent`、`failed`、`disabled` 或 `canceled`。
- `email_sent_at`：成功发送时间。
- `email_attempt_count`：已认领的发送次数。
- `email_next_attempt_at`：下一次允许重试的时间。
- `email_claimed_at` 和 `email_claim_token`：多实例认领租约。
- `email_last_error`：服务端诊断信息，不通过提醒 API 返回。

桌面待处理列表展示真实邮件状态，但不展示服务端错误细节。达到最大重试次数后提供重新发送按钮，按钮复用单条提醒更新契约并将投递状态重置为 `pending`。

## 4. 后端投递器

新增生命周期后台任务，每轮按照以下条件认领提醒：

1. 业务状态仍为 `pending`。
2. 邮件已开启且尚未发送成功。
3. 提醒时间已经到达。
4. 重试时间已经到达。
5. 发送次数未达到上限。
6. 没有有效认领，或原认领已经超过租约时间。

关系数据库使用行锁和 `skip_locked` 降低多实例重复认领风险。认领事务提交后才执行 SMTP；成功、失败和重试状态在独立事务中按认领令牌回写。

如果进程在最后一次尝试后、状态写回前退出，后台任务会在认领租约过期后将已耗尽次数的 `sending` 记录回收到 `failed`，避免永久悬挂。

默认策略：

| 配置 | 默认值 |
| --- | ---: |
| 轮询间隔 | 30 秒 |
| 认领租约 | 300 秒 |
| 最大尝试次数 | 3 次 |
| 首次重试等待 | 60 秒 |
| 每轮最大处理数 | 20 条 |

失败使用 `60 秒、120 秒` 的指数等待，第三次失败进入 `failed`。后台任务停止时不再认领新提醒，并等待当前发送结束。

## 5. SMTP 边界

- SMTP 逻辑从认证 API 抽取为共享异步邮件服务。
- 阻塞式 `smtplib` 通过工作线程执行，不阻塞 FastAPI 事件循环。
- 认证验证码邮件继续保持原有 502 错误语义。
- 未配置 SMTP 账号或密码时，提醒后台任务不会启动，也不会把提醒误标记为已发送。
- 认证开发模式仍可将验证码邮件写入日志，保持本地注册流程可用。
- 服务端只保存经过收敛的错误类型，避免把密码或底层连接信息暴露到 API。

## 6. 历史兼容

新增迁移 `009_reminder_email_delivery.py`：

- 增加邮件投递字段和组合索引。
- 历史提醒统一设为 `email_enabled=false`、`email_status=disabled`。
- 迁移完成后，新提醒使用 `true/pending` 作为数据库默认值。
- SQLite 旧库启动兼容逻辑按相同原则补字段和索引。

历史提醒不自动补发，避免上线后将积压事项集中发送到用户邮箱。

## 7. 测试契约

已补充但未执行的测试覆盖：

1. 新提醒默认开启邮件并返回待发送状态。
2. 到期邮件发送到账号邮箱，并使用小猪主题和安全正文。
3. 邮件成功后 `email_status=sent`，但桌面 `triggered_at` 保持为空。
4. 发送失败进入等待重试，并在最大尝试次数后进入 `failed`。
5. 完成或取消提醒会停止尚未发送的邮件。
6. 单条提醒可以关闭邮件且继续保留桌面提醒。
7. 邮件最终失败后可以从待处理列表重新启动投递。
8. 最后一次尝试后遗留的过期认领会自动收敛为失败状态。

## 8. 后续运行验收

恢复环境验证后，需要逐项确认：

1. 迁移 009 在空库、现有 SQLite 和现有 PostgreSQL 上成功执行。
2. 升级前历史提醒全部保持邮件关闭，不发生补发。
3. 配置真实 SMTP 后，关闭桌面应用仍能在到点后收到邮件。
4. 邮件到达后重新打开桌面应用，仍会出现小猪动作、气泡和系统通知。
5. 取消、完成和修改时间与投递任务并发时，不发送已失效提醒。
6. SMTP 暂时失败时按照 60 秒和 120 秒重试，第三次失败停止。
7. 两个后端实例同时运行时，同一提醒不会被正常重复认领。
8. 后端退出时不会继续批量认领提醒，也不会长时间阻塞关闭。
9. 中文标题、特殊 HTML 字符和换行不会破坏邮件正文或邮件头。
10. 未配置 SMTP 时状态保持待发送，桌面 UI 不显示“邮件已发送”。

SMTP 无法提供严格的端到端 exactly-once 保证。当前租约和认领令牌解决正常多实例竞争；真实邮件服务在超时后是否已接收仍需通过供应商消息 ID 或回执能力进一步增强。
